Token Economy

Token economics for LLM coding agents.

One tested source of truth for model pricing (with history), run-cost computation, and token-efficiency model selection for LLM coding-agent systems.

Get started View on GitHub $ dotnet add package TokenEconomy

What it does & why

Token Economy provides one deterministic, unit-tested library for dated model prices, run-cost calculation, and model selection.

01

Pricing catalog with history

Per-model price entries keyed by ValidFrom. A run is costed with the price valid at the run's UTC timestamp. Historic entries are kept, never overwritten.

APICode ↗
02

Cost API

ComputeCost(model, usage, atUtc) → a deterministic per-component breakdown and total. An unknown or unpriced model returns an explicit unknown — never a silent $0.

APICode ↗
03

Token-efficiency matrix

SuggestModel(…) ranks the models available right now for a task under budget pressure, each with a one-line rationale. Cost class is derived from the catalog, never restated.

Model selection — SuggestModel

Provide a task class, budget pressure, available CLIs, and a UTC instant. The API returns the eligible models in ranked order with a score, reasoning effort, and rationale. 

using TokenEconomy;

// A feature task under tight budget pressure; only Claude is available.
var ranked = ModelEfficiencyMatrix.Default.SuggestModel(
    TaskClass.Feature,
    BudgetPressure.Tight,
    availableClis: [Cli.Claude],
    atUtc: DateTime.UtcNow);

var best = ranked[0]; // An empty list means no eligible model is available.
Console.WriteLine($"{best.ModelId} @ {best.SuggestedEffort} — {best.Rationale}");

// The explicit-model API accepts a typed model id.
var sonnet = ModelEfficiencyMatrix.Default.EvaluateModel(
    KnownModels.ClaudeSonnet5,
    TaskClass.Feature,
    BudgetPressure.Tight,
    DateTime.UtcNow);
Capability fit remains a requirement. Budget pressure changes the order among eligible models. Restricted, deprecated, unavailable, and incompatible models are excluded. An empty result means wait.

Cost API

Provide a TokenUsage value and a UTC instant to ComputeCost. The result is a CostBreakdown with component costs and a nullable total. 

using TokenEconomy;

var breakdown = ModelPriceCatalog.Default.ComputeCost(
    KnownModels.ClaudeOpus48,
    new TokenUsage(Input: 250_000, Output: 12_000, CacheRead: 40_000),
    DateTime.UtcNow);

if (breakdown.HasPrice)
    Console.WriteLine($"{breakdown.Total} {breakdown.Currency}"); // approximately 1.57 USD
else
    Console.WriteLine(breakdown.Status); // UnknownModel or NoPriceForDate
Missing prices are explicit. An unknown id returns PriceStatus.UnknownModel; a known model without a price for the requested date returns PriceStatus.NoPriceForDate. In both cases CostBreakdown.Total is null.

The breakdown

  • InputCost, OutputCost, CacheReadCost, and CacheWriteCost contain the component values.
  • Total is the sum, or null when no price applies.
  • HasPrice is true only when a concrete price was used.
  • Unconfirmed identifies a provisional catalog rate.

Prices have history

Each ModelPrice is effective from a ValidFrom UTC instant. Resolution selects the most recent entry that applies to the run timestamp. New prices add entries; they do not replace historical entries.

The seeded catalog records Claude Sonnet 5 introductory pricing followed by standard pricing from 2026-09-01 (UTC):

using TokenEconomy;

var catalog = ModelPriceCatalog.Default;
var usage = new TokenUsage(Input: 1_000_000, Output: 200_000);
var intro = new DateTime(2026, 7, 10, 0, 0, 0, DateTimeKind.Utc);
var standard = new DateTime(2026, 10, 1, 0, 0, 0, DateTimeKind.Utc);

catalog.ComputeCost(KnownModels.ClaudeSonnet5, usage, intro).Total;    // 4.00
catalog.ComputeCost(KnownModels.ClaudeSonnet5, usage, standard).Total; // 6.00

KnownModels provides typed canonical ids. String overloads remain available for configuration and external input. Use ResolvePrice(model, atUtc) when only the effective rate is needed.

Model recommendation

Token Economy keeps a model recommendation separate from the measured outcome used to evaluate it.

New: study-backed task-class routing. See the published taxonomy, HTML/UI and source-review pilots, outcome costs, and policy-safe downgrade boundaries.
01 / ESTIMATE

Describe the work before launch

TaskComplexityEstimator applies intake evidence to a versioned complexity worksheet and produces a band, confidence, point forecasts, and inspectable evidence.

02 / RECOMMEND

Compare eligible models

SuggestModel combines task fit, derived cost class, and availability into ranked choices with an auditable rationale. The caller decides whether to act on the recommendation.

03 / OBSERVE

Measure the outcome

Controlled A/B setups record success, token use, duration, and authoritative cost when available. Operational history retains outcome signals for later calibration.

What determines the complexity band

The band is calculated from the six weighted worksheet criteria:

  • Correctness risk — behavioral, contract, security, concurrency, and data-loss exposure.
  • Expected scope — anticipated changed lines and affected subsystems.
  • Context demand — adjacent contracts, historical behavior, and cross-system invariants that must be read.
  • Task uncertainty — from mechanical work to unknown cause or derived requirements.
  • Empirical confidence — the quality and coverage of comparable historical evidence.
  • Quota and cost headroom — current availability, without lowering a correctness floor.

Actual changed files, tool calls, and review feedback are outcomes for later calibration, not inputs that would leak the answer into the estimate.

The separate forecast-only intake features—touched surface, novelty, constraint density, specification ambiguity, required reading, and verification cost—inform the token, duration, and reissue point forecasts. They do not determine the complexity band.

Observed results do not update policy automatically. Historical neighbours may inform later estimates. The optional host-supplied assessment is capped, and this library does not call a model provider.

The 30-card fixtures validate pipeline mechanics. The checked results/complexity-backtest snapshot is an observational replay with limited measurement coverage and weak current accuracy. It is calibration evidence, not proof of automated-selection readiness or a causal model comparison. See the complexity design and backtest contract.

Benchmarks

Open the external benchmark price-performance matrix →

Published runs are controlled local comparisons: each variant receives the same prompt and a fresh fixture, then a deterministic command evaluates the response. They are not provider-wide capability claims.

How these studies map to established benchmarks

This harness borrows the test-verified repair shape of SWE-bench and the focused function-correctness shape of HumanEval. Its fixtures are local, deliberately small, and versioned for model-selection calibration; they are not SWE-bench or HumanEval submissions, and their results are not comparable to either leaderboard.
