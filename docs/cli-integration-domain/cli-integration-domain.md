# CLI integration and source register

**Status:** decision-pending · **Phase:** concept · **Source card:** TE-61 · **Evidence retrieval:** 2026-10-16

This is the editable TE concept Dossier. The self-contained [article](index.html) is its review surface. The proposed domain page is `docs/system/domains/cli-integration.md`, adjacent to the existing [model routing policy](../system/domains/model-routing-policy.md). The proposed machine catalog is `src/TokenEconomy/catalog/cli-capabilities.json`. Neither is implemented in this card.

The concept deliverable is inside this Dossier directory. The docs-only entry is recorded under Unreleased in the root [CHANGELOG.md](../../CHANGELOG.md).

## Alternatives

| Option | Shape | Consequence |
| --- | --- | --- |
| A. Operator notes | Keep CLI knowledge in routing notes and runner descriptors. | Version and auth differences remain difficult to validate and cite. |
| B. CLI domain with a common source register | Give each CLI a versioned capability record; cite stable IDs in one TE register. | Allows a CLI change or disputed vendor text to be tracked without changing routing policy or prices. |
| C. Provider-only records | Put capabilities under each model or provider. | Repeats headless and permission facts for every model and obscures CLI version floors. |

## Recommendation

Choose **B**. The CLI record describes what a named CLI version can do under a named auth class. The model catalog continues to own model identity and API price. Routing policy continues to choose candidates and floors. Availability snapshots continue to record time-specific quota observations. The source register owns citations, excerpts, snapshots, conflict links, and verification dates. No CLI capability, quota observation, or vendor text should silently become a routing permission.

### Domain contract

One record per `cliId` (`claude-code`, `codex`, `agy`, `gemini-cli`) contains version ranges, headless invocation, prompt transport, output and event schema, continuation, timeout, permissions, model discovery, quota topology and visibility, auth modes, and model floor observations. Gemini CLI is historical in TE; the [Google migration guide](https://antigravity.google/docs/gcli-migration) describes migration to `agy`, while the [Gemini CLI headless reference](https://geminicli.com/docs/cli/headless/) remains useful for historical runs. Historical does not assert that Google has discontinued Gemini CLI.

Every fact is a `{value,evidence}` pair. `null` with `status: unknown` is distinct from `false`, zero, or an empty list. A `versionRange` scopes the behavior; a source's retrieval date does not establish the earliest supporting binary. A model floor has separate `proven-minimum`, `works-at`, `fails-at`, `bounded`, and `unknown` states, plus effective model identity. Discovery, selection, successful execution, and actual model used are separate evidence steps.

The [CLI schema proposal](cli-capabilities.schema.proposal.json) and [source schema proposal](source-register.schema.proposal.json) are Draft 2020-12 documents kept outside the build. The [four proposed CLI records](cli-capabilities.seed.proposal.json) exercise the schema, including explicit unknowns and unpromoted operator observations. The sample [source register](source-register.seed.proposal.json) contains 34 live-source entries and their 2026-10-16 retrieval dates. These seeds are design artifacts, not a completed catalog migration.

### Quota topology

Quota is a set of independent windows and pools, not one scalar. Each row needs plan tier, auth class, pool ID and label, window kind (`five-hour`, `weekly`, other), unit, remaining/used if exposed, observed-at time, reset time if exposed, and source ID. Unknown amounts remain null. `agy`'s [plans](https://antigravity.google/docs/plans) give broad five-hour and weekly rules, but the TE-61 operator note describes three Google AI Pro pools: Gemini Flash + Pro (five-hour and weekly), Claude and GPT models (five-hour and weekly), and Gemini 4 Argon (weekly only). It also supplies the text “Quota is consumed proportionally to the cost of the tokens.” These pool labels and wording are **unpromoted operator observations** until a redacted, dated, version-pinned capture or vendor text is attached. No account identifier or raw meter belonging to a person enters this public Dossier.

The older input assertion that `agy -p "/usage"` sends `/usage` to the model is version dependent and now conflicts with Google's dated v1.1.11 changelog. Record the older behavior as a historical observation whose version is unknown; represent current capability as documented since v1.1.11, subject to a runtime probe. Likewise, store the v1.2.6 timeout statement and the current headless reference as a conflict, rather than choosing one silently. [[google-agy-change-1.1.11](https://antigravity.google/docs/changelog?tab=cli)], [[google-agy-change-1.2.6](https://antigravity.google/docs/changelog?tab=cli)], [[google-agy-headless](https://antigravity.google/docs/cli/headless/)]

### API boundary

First implementation: no new runtime endpoint. Add a read-only domain page, a machine catalog, and source register consumed by existing catalog generation. The routing policy may reference `cliId` plus a required model/CLI/auth combination, but must not infer policy from vendor quotes. A later read-only API can expose `GET /cli-capabilities?cliId=&version=&authClass=` and `GET /sources/{id}` only when a caller needs them; its payload should include `unknown`, `stale`, and `conflicted` states rather than smoothing them into booleans. Credentials, account-specific quota values, and legal conclusions are outside the public API.

## Evidence

### Register contract

The single proposed register stores stable source ID, URL, title, publisher, publication date (nullable), retrieval date, evidence class, confidence, verbatim excerpt for normative or contested claims, full-page archive URL or content SHA-256, supersedes/superseded-by, and known conflicts. Own measurements additionally require anonymized method, date, CLI version, auth class and plan tier; account identifiers are forbidden. The [register schema](source-register.schema.proposal.json) expresses the shape. The [seed](source-register.seed.proposal.json) records source hashes; one OpenAI page has a stored-extract hash because its raw page blocked direct archival retrieval, and therefore needs a full snapshot before catalog promotion. A hash records retrieved bytes, not proof that the page was unchanged before retrieval.

Evidence classes are exactly: `primary vendor documentation`, `vendor announcement or changelog`, `independent measurement or benchmark operator`, `own measurement`, `secondary press`, `forum or social post`. Confidence is an assessment of fit to a specific claim, not a source popularity score. A secondary press or forum source may corroborate but never be the sole basis of a catalog value. Conflicts stay linked in both directions, with scope and date in `conflictNote`; newer text does not automatically supersede older text if auth context differs. Unknown stays unknown. At render time, `verifiedOn` more than **30 calendar days** old shows `stale`; this is a visual review flag, not invalidation of historical price or benchmark values. A historical observation has its own immutable observed date and a separate last-verification date.

The seed checks all requested live URLs on 2026-10-16. Google docs confirm the FAQ, clause 6, plans, CLI credits, headless and changelog passages [[google-agy-faq](https://antigravity.google/docs/faq/)], [[google-agy-terms](https://antigravity.google/terms/)], [[google-agy-plans](https://antigravity.google/docs/plans)], [[google-agy-credits](https://antigravity.google/docs/cli/credits/)], [[google-agy-headless](https://antigravity.google/docs/cli/headless/)], [[Google changelog](https://antigravity.google/docs/changelog?tab=cli)]. ### Migration

1. Inventory every factual field and row in `model-prices.json`, dated price snapshots, benchmark results/types, and routing evidence. Split compound prose into claims only where different sources support different facts. Do not change values.
2. Deduplicate existing `sourceUrls` and `sourceUrl` by canonical URL **plus version/claim scope**, issue stable IDs, retrieve and archive primary pages, and record publication/retrieval dates. Keep historical page versions separate. Do not convert a URL into a primary source just because its text claims a value.
3. Add `sourceIds` beside legacy fields during one compatibility window. `source` becomes an optional human summary rendered from IDs; `sourceUrls` and benchmark `sourceUrl`/`additionalSourceUrls` remain as compatibility fields until all consumers migrate. `verifiedOn` becomes a claim-level `verifiedOn` tied to a documented review event; historical `validFrom` and `publishedAt` remain distinct. `unconfirmed` maps to `evidenceStatus: unconfirmed` plus a reason, not to zero confidence or a changed price.
4. For benchmark records, keep benchmark operator, version, model, effort, score unit, sample denominator/method and retrieval date together. A secondary news article already present in `benchmark-results.json` may remain as corroboration, but add a benchmark-operator source or mark the score unresolved. Backfill existing scores retroactively under decision D3; never regenerate scores by reading a newer live leaderboard.
5. Once coverage is complete, remove legacy fields in a versioned catalog/schema migration and publish a compatibility note. Preserve immutable price snapshots and report any before/after numeric diff as a separate review.

### Validation and rendering

CI checks JSON Schema; unique IDs; resolvable citations; source publication/retrieval chronology; required quote for normative, contested, limit, and price claims; a full-page snapshot or verified archive link for promoted values; reciprocal conflict/supersession links; no account identifiers; and at least one source ID for every catalog record and every independently factual nested record. The proposal seed intentionally has provisional model-floor rows without registered raw probes; these must fail the promoted-catalog gate until evidence is attached or the rows become explicit unknowns. A secondary/forum-only citation fails. Unknown values pass with an explicit `unknown` status and an evidence gap reason; they do not pass as known. The validator reports stale facts separately from schema failures. It should not compare source text to inferred legal meanings. Structured docs and generated website claims must carry source IDs; prose-only pages receive an editorial citation audit until a tractable linter exists.

Render a TE documentation page listing claims, source IDs, excerpts, dates, snapshot links/hashes and conflict badges; render a website page using the existing TE website layout with filters for CLI, model, evidence class and freshness. Both pages are generated from the same register and catalog. Keep a direct link from each public price, release-date, benchmark and CLI fact to its cited source detail. For operator measurements, show anonymized method and result only. No screenshot of an existing TE product surface is used here: this Dossier proposes new surfaces and cites vendor documents, and makes no claim about a current visual TE page.

## Open decisions

| ID | Decision | Working recommendation | Alternative and consequence |
| --- | --- | --- | --- |
| D1 | Placement of vendor usage-term excerpts | Keep verbatim excerpts in the public source register and its page; keep only stable IDs and neutral context states in `cli-capabilities.json`. | Put excerpts inside capability rows; duplicates volatile text and obscures conflicts. |
| D2 | Staleness threshold | 30 calendar days from `verifiedOn`, rendered as a warning across current facts; preserve historical observation dates. | 90 days reduces review load but leaves changing CLI and terms text visibly fresh for longer. |
| D3 | Benchmark coverage | Backfill all existing benchmark rows retroactively, with staged unresolved states and no score rewrite. | Prospective-only coverage leaves old cited numbers outside the promised source base. |
| D4 | CLI API | Start with catalog and generated pages; add read-only API only when a consumer needs it. | Implement API now; increases contract surface before records stabilize. |
| D5 | Model floor promotion | Require an identity-confirmed successful probe at the claimed minimum and a lower-version failure or dated vendor floor statement. | Treat first successful version as minimum; can hide earlier support and silent fallback. |

Each recommendation is the working decision for promoted implementation cards unless an operator decision recorded later selects another option. Sight review and acceptance follow delivery.

## Implementation cards

The [workbench manifest](workbench.json) contains implementation-ready `promptMarkdown` for four workflow-sized cards: (1) CLI domain/catalog, (2) source register/CI, (3) price and benchmark migration, and (4) pages and verification probes. This Dossier does not modify library code, catalogs, website code, tests, or build files.
