02The two hard findings

The complexity-estimate paragraph is factually wrong — the operator's suspicion (“machen wir das so?”) is confirmed: no.

The page (line ~377) claims the estimate is informed by touched surface, dependency fan-out, novelty, constraint density, specification ambiguity, required reading and verification cost. In code, every one of those is stamped forecast-only intake feature (TaskComplexityEstimator.ForecastDimensions()) and feeds the token/duration/reissue point forecast — not the complexity band. The band is driven by the six routing-worksheet criteria: correctness risk, expected scope, context demand, task uncertainty, empirical confidence, quota/cost headroom.

Evidence: TaskComplexityEstimator.cs ~510–539 and 214–216; canonical worksheet in docs/concepts/upfront-task-complexity.md. Fix in card TE-34, point 4.

claude-mythos-5 cannot be deleted naively — a partial removal crashes the process at load.

ModelEfficiencySeed builds a profile per routing-policy row; the ModelEfficiencyMatrix constructor throws when a profile has no pricing-catalog entry, and ModelEfficiencyMatrix.Default is an eagerly-initialized static. model-prices.json and model-routing-policy.json must be cleaned in the same commit. 12 files reference the model; the “benchmark case” it contributes is literally a CLI access-denied message rendered as capability data.

Evidence: ModelEfficiencySeed.cs 10–23, ModelEfficiencyMatrix.cs 45–46. Removal in card TE-32; target-list cleanup in TE-35.

  • 30-card live-orchestrator backtest snapshot, 2026-07-25;

05Benchmark rigor — the credibility gaps

  • Two published studies total. The only coding A/B study (palindrome-repair) is one trivial one-file fixture, 2 variants, repetitions: 1, zero Claude coverage.
  • The live routing policy's only real Claude route (claude-sonnet-5/high, providerFallbacks[0]) has never been benchmarked. Its authority rests on an unspecified “small favorable feature cohort”.
  • 27% of the document-to-text matrix rows are infrastructure crashes (Codex-CLI Windows sandbox bug; restricted-model access denial) rendered identically to genuine capability misses.
  • Four catalog models were never benchmarked (claude-opus-5, gpt-5.6-luna, gpt-5.6-terra, gpt-5.4-mini); one benchmarked model (claude-opus-4-1) has retired with no flag on the page.
  • No coherent methodology documentation exists; the knowledge lives in schemas, harness code and scripts.

Evidence: benchmarks/setups/palindrome-repair.json, benchmarks/document-to-text/curated-hard-cases.json, src/TokenEconomy.Benchmarks/Program.cs 56–108 vs. 144–191, model-routing-policy.json 157–167.

06UX / API ergonomics

  • Code samples are monochrome monospace boxes with hand-tagged comments only; the site is deliberately zero-dependency and static — highlighting therefore lands as a small inline vanilla-JS tokenizer with theme-aware token colors (no CDN, no build step).
  • The C# API is 100% string-keyed for model ids. Typed design in TE-33: ModelId readonly record struct (implicit to string, explicit from string) + generated KnownModels constants, committed and drift-tested — matching the repo's generate+commit+CI-check idiom, no Roslyn.
  • The much-touted matrix (ModelEfficiencyMatrix.Describe()) is never actually rendered on the page; the charts are. TE-34 renders it as a generated artifact.
  • The three fetch()-driven sections silently break under file:// — the exact preview path DEPLOY.md recommends. TE-34 fixes docs and adds a visible degraded state.
